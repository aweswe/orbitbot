## 2. Apache-2.0 obligations relevant to this distribution

1. **Section 4(a):** give recipients a copy of the License. `LICENSE` is retained and copied into
   the web bundle, desktop app resources, mobile native projects, and Docker image.
2. **Section 4(b):** cause modified files to carry prominent notices stating that the recipient
   changed the files. The repository has 2,494 files classified as `upstream-modified`.
3. **Section 4(c):** retain all copyright, patent, trademark, and attribution notices from the
   source form. The repository retains `ATTRIBUTION.md`, `NOTICE`, and the upstream license text.
4. **Section 4(d):** if the work includes a NOTICE file, include its attribution notices. No
   upstream NOTICE was found.
5. **Section 6:** the license does not grant trademark rights. The repository does not claim
   ownership of Rakazo marks; Orbit marks are separate.
6. **Section 7:** a NOTICE may add attribution statements, but not modify the license.

## 3. Current implementation

- `NOTICE` contains the derivative and modification statement.
- `ATTRIBUTION.md` contains upstream project, URL, license, and derivative status.
- `THIRD_PARTY_NOTICES.md` contains the derivative statement, direct dependency licenses, reviewed
  obligations, and bundled-asset status.
- `compliance/modified-files.md` lists the files whose content differs from the inferred upstream
  baseline. It is generated from `compliance/provenance.json`.
- `compliance/modification-policy.json` records that the Section 4(b) policy is pending.
- Web: `NOTICE`, `LICENSE`, `ATTRIBUTION.md`, `THIRD_PARTY_NOTICES.md`, and
  `compliance/modified-files.md` are present in the production web bundle.
- Desktop: the unsigned macOS `.app`, `.dmg`, and `.zip` include the same files in
  `Contents/Resources`; the web bundle inside the app includes its own copies.
- Docker: the Dockerfile copies `LICENSE`, `NOTICE`, `ATTRIBUTION.md`,
  `THIRD_PARTY_NOTICES.md`, and `compliance/modified-files.md` into `/usr/share/doc/orbit`.
- Mobile: the Expo config plugin copies `LICENSE`, `ATTRIBUTION.md`, `NOTICE.txt`,
  `THIRD_PARTY_NOTICES.txt`, `compliance/modified-files.md`, and the LGPL text into the generated
  iOS app resources and Android `assets/legal` directory. Android debug and release-variant APKs
  and a release AAB were built and inspected, but no production-signed store build was produced in
  this sprint.

## 4. Proposed Section 4(b) policy

The proposed policy is a **distribution-level modification notice plus a generated per-file
manifest**, rather than editing 2,494 source files:

1. `NOTICE` prominently states that the work is derived from Rakazo and that Rakazo-derived files
   have been modified.
2. `compliance/modified-files.md` identifies every file whose content differs from the inferred
   baseline.
3. Every binary distribution ships `NOTICE`, `ATTRIBUTION.md`, `THIRD_PARTY_NOTICES.md`, the
   Apache-2.0 `LICENSE`, and the manifest.
4. Source distributions ship the same files at the repository root.
5. The manifest is regenerated from the provenance inventory for every release and included in the
   release artifact, not only linked from a repository.

## 5. Example per-file notice

If counsel requires an in-file notice rather than a manifest, the proposed form is:

```text
// Modified for Orbit Bot from the Rakazo project.
// See NOTICE and compliance/modified-files.md for the derivative and modification statement.
```

The same two lines would be added to each modified source file. This is mechanically possible but
would itself change 2,494 files and should be a deliberate, reviewed commit.

## 6. Distribution-level notice strategy

- Preserve the Apache-2.0 text verbatim.
- Preserve all upstream copyright and attribution notices that exist in the source.
- Keep the Rakazo derivation statement visible in every client distribution.
- Do not use the Rakazo name or logo as an Orbit mark or in a way that implies endorsement.
- Keep the LGPL-3.0 text and source-availability statement for the Sharp/libvips binary in
  distributions that include it.
- Keep the node-forge BSD-3-Clause election and notice where that package is distributed.
- Keep `THIRD_PARTY_NOTICES.md` generated from installed dependency data; do not hand-write a
  package list that can drift from the lockfile.

## 12. Decisions requiring legal counsel

These are the exact questions to record in counsel's response. No approval is implied by this
packet.

1. **Section 4(b) method.** Does a distribution-level `NOTICE` plus the generated 2,494-entry
   changed-file manifest satisfy the requirement that modified files "carry prominent notices
   stating that you changed the files"?
2. **In-file alternative.** If the manifest is insufficient, is a short header in every modified
   source file required; what exact wording must it use; must it name the modifying entity; and
   does it need to appear in generated, minified, or vendored files?
3. **Compiled bundles.** Does a minified web bundle or native application count as a modified file
   for Section 4(b), or is the source manifest plus bundled notices sufficient?
4. **Section 4(c) and 4(d) wording.** Are `ATTRIBUTION.md`, `NOTICE`, upstream copyright notices,
   and the third-party notices sufficient, and is any additional upstream notice text required?
5. **Trademark and endorsement.** Does use of the Rakazo name, logo, or upstream marks in
   attribution create a trademark, endorsement, or confusion issue; what disclaimer wording is
   required for Orbit/Forion branding?
6. **Inferred baseline.** Is the inferred upstream baseline adequate for identifying modified
   files, given the squashed import history; must the inference method and baseline commit be
   disclosed in the release record?
7. **LGPL-3.0 components.** What written-offer or source-availability statement is required for
   the Sharp/libvips binary in desktop and server distributions, and does the Docker image
   trigger additional obligations?
8. **App-store surfaces.** Do Apple App Store and Google Play require an in-app legal/notices
   screen beyond the bundled files and store listing metadata?
9. **Third-party notices.** Is the generated dependency notice sufficient for all 2,193 resolved
   dependencies, including transitive, optional, and platform-specific packages that are not
   installed on this host?
10. **AI-assisted modifications.** Does the project need to disclose AI-assisted modification or
    authorship in the copyright/attribution notices, and if so, in what wording?
11. **Public history.** Does the public repository's historical exposure of private infrastructure
    metadata, or the removal of documents from the working tree without rewriting history,
    require a legal notification, disclosure, or takedown assessment independent of the security
    incident?
12. **Release record.** Must counsel approve the final manifest and notice bundle before every
    release, or can a documented policy approval cover subsequent generated manifests?
